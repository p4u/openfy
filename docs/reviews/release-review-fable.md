## Security

### MAJOR-1: the production signing key appears to have been generated by the implementing agent, not by the maintainer

- Where: `docs/RELEASING.md:44-48` (fingerprint `1D:B9:EE:...:B2:63`), `docs/RELEASING.md:147-148` (documented
  `-dname "CN=openfy, O=openfy"`), and on this machine `~/.config/openfy/openfy-release.jks` +
  `keystore.properties`, both created 2026-10-10 01:35, 30 min before commit `33cd413` (02:04).
- Evidence: the APK I built here is signed with exactly the fingerprint written in RELEASING.md, and its DN is
  `CN=openfy, O=openfy research`, not the `O=openfy` the docs say. The spec (§1.4) says the keystore is created
  "once, offline, by the maintainer".
- Failure scenario: the maintainer publishes `v0.1.0` signed with a key they never consciously created or backed
  up. After that first release the key is permanent (every installed copy only accepts updates from it). Losing the
  laptop = losing the ability to ever update; and the store/key passwords are plaintext in a 0600 properties file.
- Fix (before the first `release: published`, no code change):
  1. Maintainer decides: adopt this key or regenerate one yourself with the documented `keytool` command. If
     regenerating, re-run RELEASING.md steps 2-3 (secrets + `OPENFY_RELEASE_CERT_SHA256`), and update the
     fingerprint in `docs/RELEASING.md:47` and `:52`.
  2. Either way, back up the `.jks` and passwords offline now (RELEASING.md already demands it), and fix
     `docs/RELEASING.md:148` to match the DN actually in use (or regenerate with the documented DN).

### MINOR-1: nothing in the repo makes the `release` environment's reviewer gate mandatory

- Where: `.github/workflows/release.yml:28` (`environment: release`), `docs/RELEASING.md:22-25` ("Optional but
  recommended").
- Who can reach the secrets today: only `release: published` and `workflow_dispatch`, both of which need write
  access to `p4u/openfy`. Fork PRs cannot (no `pull_request` trigger; a dispatch on a fork runs with the fork's
  empty environment and fails at `release.yml:91`). Dependabot cannot trigger either event. So: maintainer plus any
  future collaborator with write. The dry run is exactly as powerful as a release in terms of key use (it signs
  whatever branch it was dispatched on and publishes the signed APK as a public artifact).
- Fix: in RELEASING.md step 1 make "Required reviewers" the default, not optional, and add a repository ruleset
  restricting creation of `v*` tags to admins (one `gh api` call, document it next to the environment command).
  Note that for a sole maintainer the reviewer gate only protects against a compromised collaborator or app, not
  against the maintainer's own account; say so, as the doc already does.

### MINOR-2: `environment` deployment-branch policy would break tag builds if ever enabled

- Where: `.github/workflows/release.yml:28`. `release: published` runs with `GITHUB_REF=refs/tags/vX.Y.Z`.
- Failure scenario: maintainer later restricts the `release` environment to `main` only (a natural reaction to
  MINOR-1). Every real release then fails with "Branch 'v0.1.0' is not allowed to deploy to release" before any
  step runs; dry runs from `main` keep working, which hides the breakage.
- Fix: RELEASING.md step 1: if a deployment branch policy is set, use "Selected branches and tags" and add the
  pattern `v*`. (Spec §1.3 updated with the same note.)

## Correctness

### MINOR-3: leading zeros are accepted, so two tags can map to one `versionCode`

- Where: `tools/version-code.sh:11` (`[0-9]+`), `app/build.gradle.kts:11` (`\d+`).
- Failure scenario: `v01.2.3` is accepted (`tools/version-code.sh v01.2.3` prints `01.2.3 1020399`, tested), gets
  the same `versionCode` as `v1.2.3`, and the APK carries `versionName='01.2.3'`. The updater's semver compare
  then sees two distinct strings with equal codes. Operator error only, but cheap to close and semver forbids it.
- Fix: in both places use `(0|[1-9][0-9]*)` for X, Y, Z and `([1-9][0-9]?)` for N; add `v01.0.0` and
  `v1.0.0-rc.01` to both reject lists. Keep the spec regex as the loose form or tighten it the same way (I left
  the spec regex alone; tighten both at once if you do it).

### MINOR-4: any single `OPENFY_*` env var fails *every* Gradle invocation, not only signed ones

- Where: `app/build.gradle.kts:65-67`.
- Failure scenario: a developer with, say, `OPENFY_KEY_ALIAS` exported for unrelated reasons cannot run
  `./gradlew help` or `assembleDebug` (reproduced: `OPENFY_KEYSTORE_FILE=/x ./gradlew help` fails at
  configuration). The spec said "first hit wins"; the implementation says "all four or nothing". The stricter rule
  is better (a half-configured env silently falling through to the properties file would be worse), so I have
  updated the spec to match rather than asking for a change. Same applies to a properties file missing a key
  (`:76-77`).
- Fix: none required; documented in RELEASING.md:121-122 already.

### MINOR-5: RELEASING.md refers to CI on `main` that does not exist

- Where: `docs/RELEASING.md:109-110` ("Do not publish a release for a tag whose commit has not passed CI on
  `main`"). There is no CI workflow; the release workflow itself is the only place tests run.
- Fix: reword to "the release workflow runs tests and lint before signing; a red run uploads nothing", or add a
  minimal `ci.yml` (tests + lint on push/PR, no environment, no secrets). The latter is out of scope for §1.

## Consistency with the updater (§2/§3): what the updater must assume

Everything below is what `main` actually produces; the updater implementation should hard-code exactly this.

1. Release `tag_name` matches `^v(\d+)\.(\d+)\.(\d+)(?:-rc\.(\d+))?$`. `versionName` inside the APK is the tag
   minus the leading `v`, byte-identical (the workflow asserts it with `aapt2`).
2. Assets on a successful release are exactly two: `openfy-<versionName>.apk` and
   `openfy-<versionName>.apk.sha256`. The `.sha256` name does not match `^openfy-(.+)\.apk$` (anchored), so the
   "exactly one APK" rule in §2.1 holds.
3. `.apk.sha256` body: `<64 lowercase hex><two spaces>openfy-<versionName>.apk<LF>`, one line, nothing else. Parse
   the first whitespace-delimited token; accept upper-case hex defensively.
4. GitHub's asset `digest` is `"sha256:<64 lowercase hex>"` for assets uploaded by `gh release upload`; it is
   recomputed when `--clobber` replaces an asset. Prefer it over the `.sha256` asset (§2.3 policy unchanged).
5. Package `dev.openfy`, `versionCode = X*1_000_000 + Y*10_000 + Z*100 + (final ? 99 : N)`. The updater does not
   need the formula (it reads the archive's own `versionCode`), but if it ever asserts it, use this one.
6. Signature: APK Signature Scheme v2 and v3 only, **no v1**, exactly one signer, RSA 4096, certificate SHA-256
   `1DB9EE4A581C20D389BDDC763D27C0AF0363C2640264CFFDC3444B969004B263` (subject to MAJOR-1: if the maintainer
   regenerates the key this changes). `getPackageArchiveInfo(..., GET_SIGNING_CERTIFICATES)` handles v2/v3-only
   APKs on API 26+; do not use any JAR-signature based path.
7. Timing: a published release exists for several minutes with **zero assets** (the workflow has not finished), and
   forever if the run failed. `releases/latest` will return it. Treat "no matching APK asset" as "no update", log
   it, and do not write `skipped_tag`. Writing `last_check_ms` is fine (the user sees it at the next daily check).
8. Pre-releases (`-rc.N`) never appear in `releases/latest`; dry-run artifacts never appear anywhere the updater
   looks.
9. Debug builds: `applicationId = dev.openfy.debug`, `versionName` has **no** `-debug` suffix (it is `0.0.0-dev` or
   whatever `-PversionName` was), label "openfy debug". The updater's `-dev` ordering rule in §2.4 is what keeps
   debug builds from choking on their own version string.
